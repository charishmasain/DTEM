# DTEM research revision: methods and current limits

## Unit of analysis and records

The primary evaluation unit is one exact CVE identifier (`CVE-YYYY-NNNN...`). For NVD records, association requires the record's own explicit CVE identifier; a description that merely mentions another CVE is not enough. Other CTI documents may be associated only when a complete CVE token appears in an explicit identifier, title, body, URL, or raw source payload. Broad keyword matches such as `CVE`, a product name, threat actor, or malware family are not sufficient. Documents without a publication time may remain usable in the live prototype but are excluded from historical cutoff evaluation. Historical eligibility also requires `available_at` (or auditable `collected_at`) at or before the cutoff. This avoids using later-collected copies as if they were known earlier.

Future outcome for a planned experiment: CISA KEV `dateAdded` falls strictly after cutoff and no later than cutoff + 30 days. This measures subsequent catalog inclusion, not exploitation itself; absence from KEV is not a negative exploitation label. The horizon is a proposed default and must be preregistered before final test evaluation. CVSS applies only to a CVE with a numeric CVSS base score; it is not assigned to actors or malware. If CVSS is missing, the compatibility API reports severity as unavailable and uses the emergence score alone for its prototype risk result. This missing-severity behavior is not the manuscript's 60:40 composite.

## Current indicators and transformations

Let `N` be the count of retained CTI records for the exact query. Detection Frequency counts distinct `(source, title, URL, publication timestamp)` tuples; this removes repeated identical collection rows but cannot detect republication under changed titles/URLs. Database inserts now skip that same repeated identity. Source Diversity is the count of distinct non-empty source labels after trimming whitespace and normalizing case. Alias resolution and source independence are not established; the dashboard describes these as labeled sources rather than independent channels.

The production Growth Rate remains the legacy percentage for compatibility. With `R` reports in the recent window and `P` in the preceding equal-length window, it is `(R-P)/P * 100`. If `P=0`, the implementation returns 100 when `R>0` and 0 otherwise. Live extraction anchors its adjacent equal-length windows to the analysis time; historical evaluation passes the prediction cutoff explicitly. The extractor marks growth unavailable when neither comparison window contains dated reports, and the model assigns that unavailable indicator a 0 sub-score rather than treating missingness as stable 0% growth. The added diagnostic candidate is `G = ln((R+0.5)/(P+0.5))`, using adjacent 14-day windows anchored to the same analysis/cutoff time. `alpha=0.5` is an explicit continuity correction, not tuned or validated. This candidate is not used in the production score because no development dataset exists for parameter selection. When `growth_mode` is set to `log`, `G` is mapped to a bounded sub-score by `50*(1+tanh(G/scale))` with `scale = ln(4) ~= 1.386` (config `log_growth_scale`): `G=0` maps to 50, growth saturates toward 100, decline toward 0, and it is symmetric and monotonic. `scale` is a stated design constant, not a fitted value; `growth_scale_sensitivity` reports whether conclusions move as `scale` varies. The default remains `legacy`. For an observed legacy growth percentage, the current 0–100 transform remains: `g<=-100 -> 0`; `-100<g<=0 -> 35*(g+100)/100`; `0<g<=150 -> 35+55*g/150`; `g>150 -> min(100,90+10*(g-150)/150)`. Stable observed zero growth maps to 35, and positive/negative extremes saturate. Empty evidence produces `score_status=insufficient_data`, not a numeric emergence or risk estimate. Invalid or non-finite frequency/diversity inputs map to 0; non-finite exploit tiers map to 0. Positive/negative infinite growth use the corresponding saturation boundaries, and NaN growth maps to 0.

Source Diversity sub-score remains `min(100, 25*D)` for `D>0`, else 0. Frequency remains `min(100, 100*ln(1+N)/ln(31))` for `N>0`, else 0. Weights remain frequency 0.25, growth 0.30, diversity 0.20, exploit 0.25 and must be finite, nonnegative, and sum to one. Emergence Score is their weighted sum, clipped to [0,100]. Config stage upper bounds are interpreted as continuous inclusive intervals: [0,25], (25,50], (50,75], (75,100], so fractional scores have no gaps or overlap.

Exploit evidence is represented as an ordinal tier: none 0, generic mention 25, PoC reference 50, verified code/report 75, and in-wild evidence 100. Text matching is phrase-based and conservative; explicit record evidence can still be inaccurate, copied claims may be duplicated, and these ordinal values are not probabilities. Older records without a tier retain the legacy binary normalization of 0 or 70–100 based on a Boolean and report ratio, so legacy and revised tier scores are not fully comparable until historical data is reprocessed.

For known numeric CVSS `C` in [0,10], the existing composite formula is `0.60*Emergence + 0.40*(10*C)`. If CVSS is absent, the API exposes missing severity and uses Emergence alone for compatibility; that is explicitly not a 60:40 result. Existing non-CVE scenarios receive no CVSS severity.

## Historical data workflow

`dtem.evaluation.historical` provides strict CVE matching, timestamp parsing, availability-at-cutoff filtering, KEV horizon labeling, and lead-time state handling. Captured observations should be stored as JSON Lines with source, exact CVE, publication timestamp, first availability timestamp, collection timestamp, retrieval timestamp/source URL, and raw payload. Keep retrieval manifests next to each dataset. A dated EPSS observation is eligible only for its actual score date at or before the cutoff; never forward-fill a later score. NVD `lastModified` after cutoff is a revised record and must not be substituted for its historical version.

The repository also archives the official NVD CVE History API, and can import catalog states from the official `cisagov/kev-data` Git mirror. Retrieved NVD history covers 2025-01-24 through 2025-02-25: 13,475 timestamped change events affecting 10,343 CVEs. These are NVD workflow changes, not independent CTI detections. NVD event `created` is used as an earliest-availability proxy because the API does not provide a separate public release timestamp; exact public availability is therefore unverified. KEV Git history has 330 parseable catalog snapshots from 2025-01-24 through 2026-10-23 and records 1,768 catalog state events (1,760 additions); its manifest marks one malformed mirror commit as an error. The backtester allows complete 30-day windows only inside the interval covered by intact snapshot release timestamps. The collected first EPSS historical sample remains only one CVE over three dates in January 2024 and does not overlap the NVD cohort/cutoffs; it cannot support an EPSS comparison.

An exploratory run using only NVD change history, four weekly cutoffs, and the versioned KEV catalog wrote `output/evaluation/option_a_nvd_only_exploratory.json`. It contains 25,280 CVE-cutoff rows for 9,591 CVEs; 17 rows (12 distinct CVEs) have a subsequent KEV addition in the 30-day horizon. At the unchanged DTEM threshold of 50, the descriptive confusion matrix is TP=0, FP=6, FN=17, TN=25,257. This is not a valid evaluation of multi-source DTEM: the feature source is NVD database workflow activity, not CTI, and observations from the same CVE recur at adjacent cutoffs. There is no chronological development/validation/final-test split, no date-matched EPSS for these rows, and no ablation, sensitivity, PR-AUC, confidence interval, or valid lead-time estimate. These descriptive numbers must not be presented as evidence that DTEM predicts exploitation or outperforms a baseline. No historical alert-event log exists.

The curated seven-scenario grid search and relative-time timeline are prototype-only. They are manually authored and must not be reported as empirical performance. CVSS is a severity benchmark, not temporal prediction. Any future lead time is `event_time - first_valid_alert_time`; missed events and missing timestamps have no numeric lead, alerts with a confirmed negative outcome are false alerts, and alerts after an event are negative/late. Baselines need their own observed alert times.

## Evaluation comparison layer

`dtem.evaluation.metrics` provides average precision (PR-AUC), threshold confusion metrics, and a percentile bootstrap interval for PR-AUC. Average precision is compared against the positive prevalence (`random_baseline`), never against 0.5, and is reported as undefined (`status`) whenever only one class is present. `dtem.evaluation.ablation` renormalizes the remaining weights and re-scores the *same* rows and labels with each indicator removed (leave-one-out), with each indicator alone, and across a grid of thresholds and log-growth scale values, so an indicator's contribution can be isolated rather than assumed. `dtem.evaluation.baselines` scores simple frequency, growth, source-diversity, and exploit-only proxies, CVSS severity, and date-matched EPSS on the identical rows the DTEM model uses, giving every method only cutoff-available information. `dtem.evaluation.split` partitions rows by prediction-cutoff time into development, validation, and held-out test periods (never randomly and never by CVE), counts CVEs that recur across periods, and states that weights/thresholds must be selected on development only. The temporal backtest emits all of these whenever predictions exist. They are computation tooling: on the current NVD-only exploratory cohort they are descriptive, are labeled `exploratory_nvd_only`, and are not evidence of predictive validity until run on genuine, leakage-safe, both-class CTI data.

## Reproduction status

Run `python -m dtem.evaluation.research_pipeline collect` to save current NVD and CISA KEV snapshots, `nvd-history --start YYYY-MM-DD --end YYYY-MM-DD` to collect dated NVD CVE change events, and `import-kev-history --repo PATH` after cloning `https://github.com/cisagov/kev-data` to archive versioned KEV additions, removals, and date revisions. NVD requests use at most 120-day windows, paginate, wait 6 seconds between unauthenticated requests by default, and preserve NVD event-created timestamps. Failed or malformed source data is recorded in manifests and cannot silently extend coverage. The `epss-history --cves-file ... --start YYYY-MM-DD --end YYYY-MM-DD` command retrieves actual dated FIRST EPSS scores for a pre-defined cohort. Dates are inclusive; no missing values or publication timestamps are inferred. For a cutoff, a score is eligible only when its UTC score date is strictly earlier than the cutoff's UTC calendar date, because the archive supplies a date rather than an intraday availability timestamp. EPSS values are a probability baseline for the following 30 days and are thresholded at a documented default of 0.10. Model-version changes (EPSS v1–v5) require stratification or explicit interpretation.

Use `backtest --observations ... --kev ... --epss-history ... --start ... --end ...` only with timestamped CTI JSONL and versioned KEV history or a genuine coverage sidecar. A current NVD snapshot is not automatically backfilled as CTI evidence because its present-day content cannot establish past availability. The NVD History API is historically timestamped, but represents NVD record workflow updates and must be labeled as such. The runner currently emits descriptive threshold metrics, a date-matched EPSS subset when supplied, and per-CVE-cutoff predictions; it does not implement chronological model selection, frequency/growth/rule baselines, PR-AUC, confidence intervals, or historical alert persistence. Its run on NVD-only input is exploratory and must not be represented as a completed DTEM test-set evaluation. Seven-scenario artifacts remain prototype-only.
